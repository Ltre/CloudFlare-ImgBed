## 一、最初需求和约束

### 1.1 目标

用户要求参照 **Ltre/file-tunnel** 项目的 Telegram 网盘体验，在 CloudFlare-ImgBed 的指定分支实现独立的虚拟网盘能力：

1. 多级目录管理，支持任意层级进入和路径面包屑。
2. 文件、目录在同分区和跨分区间复制、移动；跨协作者权限边界下的复制、移动也应可用。
3. 网盘分区及不同分区之间的隔离。
4. 网盘协同授权：区分只读和可写，允许同时跨多个授权分区操作。
5. 文件或目录共享链接、有效期限和撤销。
6. 单个网盘文件可选择开放静态资源 URL；默认不得无意公开私有文件。
7. 可视化文件预览，尤其是图片、文本、视频、PDF；大文件按 Range、分片或流方式读取，不能要求一次性全部载入。
8. 对外提供 **S3 标准风格 API**，覆盖本版本明确承诺的常见对象操作。
9. 直接复用 CloudFlare-ImgBed 已实现的上传通道、文件记录和存储配置；**不照搬 file-tunnel 的 SQLite 文件存储架构，也不重新开发上传系统**。
10. 所有实际改动落在 **d2tunnel-disk** 分支，分批提交避免工作丢失。

用户随后明确增加部署要求：**Cloudflare Workers 和 Cloudflare Pages 都必须支持**，Docker/Node 本地兼容可以保留，但不得在关键运行时引入 Pages/Workers 不可用的 Node.js 专属 API。

### 1.2 不在本版本自动扩张的范围

附件中对 S3 能力的明确限定：当前目标是 **常用对象操作 + Multipart Upload 的 S3 兼容子集**，而不是完整 AWS S3。版本控制、完整 IAM/ACL、所有条件请求和所有 AWS 扩展协议不是现有承诺。新增超范围功能应另开后续版本，避免无休止开发。

## 二、附件记载的六轮问答与开发演进

### 阶段 A：最初立项、架构审查与 Cloudflare 双部署约束

**用户第一次提问**：完整要求虚拟网盘、S3 API、协同及分享、文件预览、引用复用和及时提交。

**技术判断**：

- 现有 ImgBed 的核心模型以「上传文件记录」为中心，虽然已有目录属性、管理接口、Telegram/Discord 分片下载及部分 Range 支持，但缺少**独立于文件通道的目录树、分区身份与授权**。
- 因此网盘首先需要的是元数据和授权模型，而不是再造一套上传后端。
- 选用 **Cloudflare D1** 保存虚拟目录、分区、授权、分享和 S3 multipart 元数据；文件字节继续留在 ImgBed 原有 Telegram/Discord/R2 等渠道。
- 前端项目主要提供构建后的前端产物，采用独立的 **disk.html** / **disk-share.html** 页面与 API，避免重写压缩后的旧 UI。

**用户补充**：同一分支必须能部署至 Worker 或 Pages。

**对应实现方向**：

- 使用 Pages Functions 风格的请求处理函数及 Cloudflare 标准绑定。
- 由 **deploy/worker/generate-routes.js** 将 Functions 路由转换成 Workers 路由入口。
- 配合 KV、D1、R2 等绑定；不得依赖只在 Docker 可用的 Node API。
- 先实现分区/目录/权限/分享核心，再补 S3 网关、页面和回归。

**附件记录的首阶段进展**：分区目录树、跨分区操作、协同密钥与分享、静态资源 API、S3 网关、独立页面分批提交。阶段性短 SHA **631eb472cb92**；它只是记录中的一个提交节点，不代表全部功能通过验证。

### 阶段 B：补齐原有上传关联、原始文件引用一致性与 S3 Multipart

**用户再次要求继续完成**，重点转向存储安全、S3 分片和可用的直传交互。

**设计思路**：

- 网盘节点通过 **source_id** 引用原始物理文件，而非每复制一次文件就重复上传字节。复制/移动首先修改 D1 元数据。
- 如果后台管理把仍有网盘引用的物理源文件直接删除，网盘会出现悬空指针。因此给原文件删除设置引用保护；原文件 ID 变更时同步迁移引用。
- ImgBed 的上传链路不能被网盘设计替换。允许通过可选参数 **diskSpace / diskPath / diskName** 在上传完成后关联目录；即使不提供这些参数，原有上传行为保持不变。
- S3 大文件使用 **R2 Multipart Upload + D1 持久化清单**，允许 Create / UploadPart / ListParts / Complete / Abort，避免一次请求持有完整大对象内存。
- 网盘网页的直接上传仍调用原 ImgBed 上传接口，之后将成功文件关联到目标目录。

**记录中提到的具体改动和保障**：

- 在原始文件被引用时禁止危险的源删除。
- 原文件移动或改名时更新引用关系。
- 增加 S3 SigV4 认证、CORS、分片元数据和重试处理。
- 支持 CopyObject、同名覆盖、DeleteObjects 批量删除。
- S3 创建对象设置默认私有，普通未授权 **/file/** 不应因对象存于 ImgBed 底层而绕过网盘授权。
- 使用短时预览能力票据、范围读取、HEAD 和续传以保护协作与大文件流式访问。
- 设计仅对网盘 S3 产生的对象进行回收；不误删普通 ImgBed 文件。

### 阶段 D：收敛数据安全风险，继续补齐本地测试

**用户第五次提问**：继续。

**核心安全问题一：S3 CopyObject 来源完整性**

原因：如果仅验证目标对象路径的 SigV4 签名，而允许未签名的 **x-amz-copy-source** 变更，会导致一个原本合法的 PUT 请求在传输途中被用于复制别的源对象。

修改与预期：CopyObject 的源路径必须包含在已签名请求头列表中；增加「来源不参与签名」和「签名后替换来源」两种拒绝用例，预期均返回 HTTP 403。

**核心安全问题二：GC 删除中断后的引用丢失**

原因：R2 删除成功后，KV 索引删除或数据库清理可能失败。如果 GC 直接把对象从 deleting 恢复到 active，新的目录节点可能引用已经消失的物理对象。

修改与预期：

- 建立 **gc_claimed_at** 删除声明时间，状态为 deleting 时禁止创建新引用。
- 中途失败不得随意恢复 active；经过约 10 分钟的租期后允许幂等重试清理。
- 回收候选排除仍存在 Multipart 清单的源文件。
- Multipart 初始化时提前注册其 R2 源标识，减少 complete 后崩溃产生无法追踪的孤儿文件。
- 新增第四阶段数据库迁移 **v2.8.3_disk_gc_recovery.sql**；旧迁移的残留删除声明需要迁移恢复处理。

**核心维护问题三：大型分区删除**

- 把逐节点删除改为按分区批量 SQL 删除，降低大量 D1 网络往返和 Workers 执行时间风险。
- 分区尚有未完成的 Multipart 会话时，禁止删除分区并返回明确冲突。
- 对目录删除、批量删除等路径增加测试。

**Wrangler 配置判断变更——必须保留的历史纠正**：

- 附件中一度提出 Pages 不能使用自定义 **--config**，因而采用临时生成标准 wrangler.jsonc 的办法。
- 后续轮次又依据新的 Wrangler 参数资料调整为使用全局 **--config**，避免 Ctrl+C 中断遗留临时文件。
- **这两个说法在附件中前后不同。最终以实际安装的 Wrangler CLI 行为和 G1 实跑为准**，不得因文档表述认定正确。

## 2026-10-27 · G1 S3 ListObjects 分页正确性修补

### 用户要求

用户本轮要求「继续」。遵循已固定的 G0–G4 验收标准：集中修复既有功能与 G1 阻塞缺陷，不扩大原始需求。每日 QA 归档在 `docs/prompt/QA-YYYYMMDD.log`；本日开发日志唯一位置为 `docs/log/dev-20261027.md`。回复结尾写明当前阶段及可否验收。

### 本次发现的实际问题

- 原 `functions/s3/[[path]].js` 的 `listBucket()` 先按**底层对象 key**过滤 continuation-token / marker，再在页面构造循环中将多个对象折叠为共同目录前缀。
- 例：对象有 `a/one.txt`、`a/two.txt`、`b/three.txt`、`root.txt`，使用 `?list-type=2&delimiter=%2F&max-keys=1`。
- 首页返回 `<CommonPrefixes>a/</CommonPrefixes>`（实际 XML 子结构为 Prefix），但游标记录成物理对象 `a/one.txt`。次页还有 `a/two.txt`，被错误地再次折叠为 `a/`，导致同步客户端看到重复目录，增加分页次数，甚至影响遍历行为。
- 同时原实现忽略 V2 的 `start-after`；`max-keys=0` 被错误地归为默认值 1000，负值或无效参数也未严格处理。

### 设计调整

1. 先通过现有 `collectObjects()` 取得元数据文件集合。
2. 按请求 `prefix` 和 `delimiter`，将同目录文件折叠到**用户可见的逻辑目录键**（例如 `a/`），其余文件保留原 key。
3. 再针对逻辑键执行 `continuation-token`（V2）、`start-after`（V2）或 `marker`（V1），排序分页。
4. `NextContinuationToken` / `NextMarker` 返回本页最后一个**可见逻辑键**，而不是文件组中某个被隐藏的对象 key。
5. 对 `max-keys` 验证有限安全整数且非负，限制单页最大 1000。没有显式参数时使用默认 1000，显式 0 不再被解释成 1000。
6. S3 接口继续保持 ETag 语义和物理元数据隔离，未修改目录、权限或底层存储模型。
